Formal models, tests, simulators, benchmark runners and reports are supporting assurance/evaluation tools, not additional runtime security groups. Their evidence limits are described below.

The lifecycle controller's process-local digest cache is bounded and fails closed at capacity, but it is not durable or shared across controller instances. Generic Python executor callbacks remain trusted host configuration; the manifest digest does not independently prove callback-code identity. These are explicit prototype limits, not completed lifecycle guarantees. The controller's `session_id` is local audit context, not a field authenticated inside `Request` or by the transport; host code must establish the authenticated workload-to-session mapping and isolate controller instances appropriately.

## Confirmed evidence and its limits

The simulator has 30 author-written deterministic attack scenarios and 11 benign workflows. Its baselines are hand-authored comparators. This is useful for regression tests and ablations, but the scenarios are not an independent benchmark and do not establish production security effectiveness.

The generated simulator output is attached to the latest successful `main`-branch CI run as `paca-benchmark-regenerated`. The live AgentDojo model experiment is credential-dependent; the CI job can be green while its preflight and live-run steps are skipped when `OPENAI_API_KEY` is unavailable. Adapter tests and dry-run preflight do not count as live-agent evaluation.

The tests deliberately demonstrate bypasses as well as mediated controls. Direct access to raw SQLite values, raw PostgreSQL checkpoint APIs, direct Python tool calls, subprocesses and direct filesystem/network operations can escape the adapters. These are documented in [DIRECT_BYPASS_EVALUATION.md](DIRECT_BYPASS_EVALUATION.md).

## Highest-priority work

The architecture specification is the target-design reference. v0.2.0 adds explicit broker identity-binding, semantic delegation-containment, declassification, revocation-freshness, commit-linearization and cumulative conformance decisions. The v1.0.0 protocol bundle defines ten structured message types. JSON Schema validation is structural only. The current main implementation also contains strict JSON/I-JSON parsing, RFC 8785 canonicalisation, domain-separated SHA-256 digests, a reference Ed25519 message signer/verifier with configured key scopes, and a `BrokerOperationVerifier` that checks signed operation messages against a trusted session context, channel-binding digest, resolved grant reference and recomputed intent/payload digests. It derives the existing registry access-receipt shape and retains canonical signed message bytes. These are protocol-verification and request-binding primitives, not authenticated transport/session establishment, durable nonce consumption by themselves, a production identity provider, grant/revocation evaluation, provenance release checks or a resource enforcement boundary. The existing SQLite/PostgreSQL resource registry also exposes transactional logical reads and writes with active-authority, scope, quota and replay checks. The current main implementation includes trusted-principal binding to both fenced resource transactions and enforces the requested read-byte ceiling against the complete canonical response before receipt insertion or quota charging. It now includes `InProcessBrokerReadMediator`, which connects a signed v1.0.0 `read` operation for a local logical `file` resource to that transactional read path. The mediator checks the current grant's trusted issuer/audience, principal, tenant, task, purpose and persisted per-capability limit, and requires an explicit provenance-release callback before returning data. It rejects writes, deletes, queries, sends, execution, provider resources, version selectors and field projections; it is not an authenticated network service or IPC boundary. The broker message verifier also enforces a 300-second default freshness window and 30-second future clock skew. Newly issued authority records persist immutable per-capability `max_calls` and grant audience values; transactional effect, message, read and resource-commit paths cap caller/permit limits against the persisted call ceiling, and delegation cannot exceed a persisted parent ceiling or change its audience. Historical records omit absent fields to preserve canonical bytes and chain digests. No historical limit or audience is inferred, so broker mediation rejects legacy records that lack the required persisted bindings. Protocol-grant storage and typed protocol predicate/delegation semantics remain unimplemented. The merged v1.0.0 broker implementation on main includes a narrow v1.0.0 commit-permit path for local logical-file writes through `InProcessBrokerWriteMediator` (see the v1.0.0 contract documentation); this is not a general broker service, a host-filesystem writer or a remote-provider commit protocol. The bounded formal suite includes PACABroker (permit, revocation, policy epoch and read/commit checks), PACAGrant (finite-set attenuation and budget reservation) and PACAInfoFlow (conservative labels and audited declassification), alongside PACAAuth and PACALifecycle. Passing these models is not implementation-refinement, OS-isolation, provider or independent-evaluation evidence. The current main branch does include an optional separate-process Linux AF_UNIX transport for configured local read/write mediators. What remains unestablished is a deployment-enforced broker/worker boundary that makes this transport the only route to every protected resource: the library does not launch or wire the broker into every runtime, configure OS restrictions, remove raw resource/credential access from workers, or prevent alternate framework/host paths. Remote-provider commit enforcement and independently implemented cross-platform execution adapters also remain absent. Keep implementation claims scoped to tested local reference paths, and do not introduce mandatory dependencies on a particular OS, framework, protocol, policy engine or storage product.

Before further security-sensitive changes, a repository administrator must also apply and verify the `main` branch ruleset and release-tag protections described in [REPOSITORY_SECURITY_CONFIGURATION.md](REPOSITORY_SECURITY_CONFIGURATION.md). The guide is configuration guidance, not evidence that protection is currently active.


1. **Complete the trusted execution boundary.** Keep raw provider clients, credentials, database handles, issuer keys and protected stores out of agent-controlled processes. The opt-in strict Docker mode accepts only `run_command` through `PACAAgentRuntime`; it is not an OS policy and cannot stop direct bypasses. The optional AF_UNIX transport already provides a narrow separate-process path for configured local logical-file reads/writes, with UID/GID peer checks. The next step is to make a brokered profile operationally mandatory for each declared protected resource: run broker and workers under distinct service identities, wire all relevant operations through the broker, remove workers' direct access to raw stores/credentials and demonstrate denial of alternate filesystem/database/network/framework/subprocess paths. The current cross-UID fixture covers one protected-file scenario, not universal mediation.
2. **Make effect authorization unavoidable.** Route every consequential mutation through a resource broker that rechecks current authority, policy epoch, provenance, target, payload and replay/idempotency at the destination commit boundary. The new optional filesystem writer holds the local SQLite/PostgreSQL authority transaction through the real-file rename and has journal-based crash recovery; it is not mandatory, does not supply a brokered read path, and does not solve remote-provider commits. Implement provider-specific conditional commit protocols next. The v1.0.0 broker write adapter remains a logical-resource path; it does not turn protocol writes into host-filesystem writes.
3. **Complete production identity and key management.** Bind issuer requests to an authenticated principal, tenant and orchestrator-owned task. Add OIDC/workload identity, KMS/HSM-backed signing and authenticated public-key distribution. The code now supports static Ed25519 key-ring overlap and retirement by configuration; deployments still need coordinated key rollout, protected custody, rotation automation and emergency-revocation procedures.
4. **Define state consistency and recovery.** Decide which state is authoritative, bring provenance/value/operation evidence behind a compatible shared persistence model, and test crash recovery, migrations, restore/rollback and primary failover. Do not call the current PostgreSQL registry a distributed lifecycle store.
5. **Make isolation and approval boundaries explicit.** Require an isolated executor for untrusted tool code, prevent credential access from workers, and integrate a separately authenticated approval service for actions that require human approval.
6. **Prove usefulness independently.** Run matched, reproducible experiments against native, pinned baselines: CaMeL/Progent for applicable information-flow and tool-privilege cases, Multi-CaMeL for cross-agent provenance, AID-Guard for commit/recovery semantics, and AgentDojo's native `tool_filter` on supported tasks. Add memory/delegation/revocation/bypass attacks, repeat stochastic runs and report confidence intervals, benign utility, false blocks, latency and cost. Do not replace any comparator with a hand-written imitation.
7. **Obtain an independent security review.** Review the threat model, trusted computing base, API contracts, concurrency assumptions, migration/recovery and adversarial test evidence before making stronger claims.

## Claim and release discipline

Until these gates are independently tested, describe the project as a **research prototype with selected mediated-path controls and known bypasses**. Do not describe it as complete lifecycle mediation, universal agent protection, independently audited, production-ready or proven to prevent real-world prompt-injection attacks.

Passing CI means that the checked-in tests and bounded model checks pass for their defined inputs. It is not a security certification.
