# PAC++ New — implementation status and engineering gates

**Implementation snapshot baseline:** 27 November 2026, merge commit `b2e68277d2604c730fd5ae0c86a49ded20a72ef5` on `main`. This is the verified code baseline for this status update; later documentation-only commits do not change the implementation. Older architecture and evaluation documents retain their own historical baselines.

**Maturity:** research prototype. The repository contains useful reference mechanisms and integrations, but does not mediate every agent lifecycle transition and is not production-ready.

**Project boundary:** this roadmap applies only to `PACA-Plus-Plus-New`. The separate `PACA-Plus-Plus` repository is an enterprise authorization gateway and has a different architecture, codebase and evidence base.

**Architecture direction:** [ARCHITECTURE_SPECIFICATION.md](ARCHITECTURE_SPECIFICATION.md) defines the proposed open, platform-independent target architecture (Draft v0.2.0). It is a normative design proposal for future work, not a claim that the current implementation already satisfies it.

PR [#42](https://github.com/sanafirdouse2323-glitch/PACA-Plus-Plus-New/pull/42) orders broker provenance validation and protected reads/writes against `revoke_lineage()` through a shared SQLite writer reservation on one host. PR [#43](https://github.com/sanafirdouse2323-glitch/PACA-Plus-Plus-New/pull/43) separates logical and filesystem registry namespaces and preserves committed-version evidence for filesystem journal recovery. PR [#44](https://github.com/sanafirdouse2323-glitch/PACA-Plus-Plus-New/pull/44) gates Docker publication on all required non-credential-dependent validation jobs. PR [#46](https://github.com/sanafirdouse2323-glitch/PACA-Plus-Plus-New/pull/46) expands mypy coverage to selected security-critical modules and checks untyped function bodies. PR [#48](https://github.com/sanafirdouse2323-glitch/PACA-Plus-Plus-New/pull/48) adds fail-closed lifecycle enforcement and the policy-continuity evaluation contract for PACA-managed runtime calls. These changes are merged into the baseline above; their explicitly documented host, process, distributed-state and evaluation limits still apply.

The lifecycle controller's process-local digest cache is bounded and fails closed at capacity, but it is not durable or shared across controller instances. Generic Python executor callbacks remain trusted host configuration; the manifest digest does not independently prove callback-code identity. These are explicit prototype limits, not completed lifecycle guarantees.

## Confirmed evidence and its limits

The simulator has 30 author-written deterministic attack scenarios and 11 benign workflows. Its baselines are hand-authored comparators. This is useful for regression tests and ablations, but the scenarios are not an independent benchmark and do not establish production security effectiveness.

The generated simulator output is attached to the latest successful `main`-branch CI run as `paca-benchmark-regenerated`. The live AgentDojo model experiment is credential-dependent; the CI job can be green while its preflight and live-run steps are skipped when `OPENAI_API_KEY` is unavailable. Adapter tests and dry-run preflight do not count as live-agent evaluation.

The tests deliberately demonstrate bypasses as well as mediated controls. Direct access to raw SQLite values, raw PostgreSQL checkpoint APIs, direct Python tool calls, subprocesses and direct filesystem/network operations can escape the adapters. These are documented in [DIRECT_BYPASS_EVALUATION.md](DIRECT_BYPASS_EVALUATION.md).

## Highest-priority work

The architecture specification is the target-design reference. v0.2.0 adds explicit broker identity-binding, semantic delegation-containment, declassification, revocation-freshness, commit-linearization and cumulative conformance decisions. The v1.0.0 protocol bundle defines ten structured message types. JSON Schema validation is structural only. The current main implementation also contains strict JSON/I-JSON parsing, RFC 8785 canonicalisation, domain-separated SHA-256 digests, a reference Ed25519 message signer/verifier with configured key scopes, and a `BrokerOperationVerifier` that checks signed operation messages against a trusted session context, channel-binding digest, resolved grant reference and recomputed intent/payload digests. It derives the existing registry access-receipt shape and retains canonical signed message bytes. These are protocol-verification and request-binding primitives, not authenticated transport/session establishment, durable nonce consumption by themselves, a production identity provider, grant/revocation evaluation, provenance release checks or a resource enforcement boundary. The existing SQLite/PostgreSQL resource registry also exposes transactional logical reads and writes with active-authority, scope, quota and replay checks. The current main implementation includes trusted-principal binding to both fenced resource transactions and enforces the requested read-byte ceiling against the complete canonical response before receipt insertion or quota charging. It now includes `InProcessBrokerReadMediator`, which connects a signed v1.0.0 `read` operation for a local logical `file` resource to that transactional read path. The mediator checks the current grant's trusted issuer/audience, principal, tenant, task, purpose and persisted per-capability limit, and requires an explicit provenance-release callback before returning data. It rejects writes, deletes, queries, sends, execution, provider resources, version selectors and field projections; it is not an authenticated network service or IPC boundary. The broker message verifier also enforces a 300-second default freshness window and 30-second future clock skew. Newly issued authority records persist immutable per-capability `max_calls` and grant audience values; transactional effect, message, read and resource-commit paths cap caller/permit limits against the persisted call ceiling, and delegation cannot exceed a persisted parent ceiling or change its audience. Historical records omit absent fields to preserve canonical bytes and chain digests. No historical limit or audience is inferred, so broker mediation rejects legacy records that lack the required persisted bindings. Protocol-grant storage and typed protocol predicate/delegation semantics remain unimplemented. The merged v1.0.0 broker implementation on main includes a narrow v1.0.0 commit-permit path for local logical-file writes through `InProcessBrokerWriteMediator` (see the v1.0.0 contract documentation); this is not a general broker service, a host-filesystem writer or a remote-provider commit protocol. The bounded formal suite includes PACABroker (permit, revocation, policy epoch and read/commit checks), PACAGrant (finite-set attenuation and budget reservation) and PACAInfoFlow (conservative labels and audited declassification), alongside PACAAuth and PACALifecycle. Passing these models is not implementation-refinement, OS-isolation, provider or independent-evaluation evidence. The current main branch does not provide a separate broker process/IPC trust boundary, remote-provider commit enforcement, or independently implemented cross-platform execution adapters. Keep implementation claims scoped to tested local reference paths, and do not introduce mandatory dependencies on a particular OS, framework, protocol, policy engine or storage product.

Before further security-sensitive changes, a repository administrator must also apply and verify the `main` branch ruleset and release-tag protections described in [REPOSITORY_SECURITY_CONFIGURATION.md](REPOSITORY_SECURITY_CONFIGURATION.md). The guide is configuration guidance, not evidence that protection is currently active.


1. **Define and enforce the trusted execution boundary.** Keep raw provider clients, credentials, database handles, issuer keys and stores out of agent-controlled processes. The runtime has an opt-in strict mode that accepts only `run_command` and requires the concrete Docker executor for calls routed through `PACAAgentRuntime`; the executor is immutable and supports sync and async entry points. File, memory and provider actions remain disabled in this mode until brokered access exists. This is not an OS security boundary: direct framework, subprocess, host filesystem and provider-client bypasses remain open. Next, put the runtime behind a distinct OS identity and trusted broker, then test real host-level bypasses.
2. **Make effect authorization unavoidable.** Route every consequential mutation through a resource broker that rechecks current authority, policy epoch, provenance, target, payload and replay/idempotency at the destination commit boundary. The new optional filesystem writer holds the local SQLite/PostgreSQL authority transaction through the real-file rename and has journal-based crash recovery; it is not mandatory, does not supply a brokered read path, and does not solve remote-provider commits. Implement provider-specific conditional commit protocols next. The v1.0.0 broker write adapter remains a logical-resource path; it does not turn protocol writes into host-filesystem writes.
3. **Complete production identity and key management.** Bind issuer requests to an authenticated principal, tenant and orchestrator-owned task. Add OIDC/workload identity, KMS/HSM-backed signing and authenticated public-key distribution. The code now supports static Ed25519 key-ring overlap and retirement by configuration; deployments still need coordinated key rollout, protected custody, rotation automation and emergency-revocation procedures.
4. **Define state consistency and recovery.** Decide which state is authoritative, bring provenance/value/operation evidence behind a compatible shared persistence model, and test crash recovery, migrations, restore/rollback and primary failover. Do not call the current PostgreSQL registry a distributed lifecycle store.
5. **Make isolation and approval boundaries explicit.** Require an isolated executor for untrusted tool code, prevent credential access from workers, and integrate a separately authenticated approval service for actions that require human approval.
6. **Prove usefulness independently.** Run matched, reproducible live-agent experiments against maintained baselines (including CaMeL/Progent where applicable), add memory/delegation/revocation/bypass attacks, repeat stochastic runs and report confidence intervals, benign utility, false blocks, latency and cost.
7. **Obtain an independent security review.** Review the threat model, trusted computing base, API contracts, concurrency assumptions, migration/recovery and adversarial test evidence before making stronger claims.

## Claim and release discipline

Until these gates are independently tested, describe the project as a **research prototype with selected mediated-path controls and known bypasses**. Do not describe it as complete lifecycle mediation, universal agent protection, independently audited, production-ready or proven to prevent real-world prompt-injection attacks.

Passing CI means that the checked-in tests and bounded model checks pass for their defined inputs. It is not a security certification.
